# موقع سي كافيه ولوحة التحكم

## التشغيل على جهازك

افتح `start.bat` بنقرة مزدوجة، فتفتح لوحة التحكم تلقائيًا. أو من الطرفية:

```bash
node server.js
```

- الموقع: `http://localhost:3000/`
- لوحة التحكم: `http://localhost:3000/admin/`

لا يحتاج المشروع إلى `npm install`، يكفي Node.js الإصدار 18 أو أحدث.

## كيف يعمل

- كل محتوى الموقع في `data/content.json`، ويُعدَّل من لوحة التحكم.
- عند النشر يولّد الخادم `index.html`، فلا تعدّل هذا الملف يدويًا لأنه سيُستبدل.
- مخطط الحقول في `lib/schema.js`، وقالب الصفحة في `lib/render.js`.

## الوصول إلى لوحة التحكم

لا توجد كلمة مرور:

- من الجهاز الذي يشغّل الخادم تفتح اللوحة مباشرة.
- من أي جهاز آخر افتح الرابط السري من «الإعدادات» مرة واحدة، فيتذكر الجهاز الإذن.
- أي طلب آخر إلى `/admin` يحصل على 404.

من يملك الرابط السري يستطيع تعديل الموقع. وإذا تسرّب غيّره من «الإعدادات».

## النشر على خادم

ارفع المجلد كاملًا إلى أي خادم يدعم Node.js، ثم شغّل `npm start`. يقرأ الخادم المنفذ من المتغير `PORT`.

- يجب أن يكون مجلد `data/` ومجلد `assets/uploads/` على تخزين دائم، وإلا ضاعت التعديلات والزيارات عند إعادة التشغيل.
- لا يعمل التتبع على الاستضافات الثابتة التي لا تشغّل Node.js.
- بعد النشر أضف رابط الموقع في «كل المحتوى ← البحث والمشاركة».

## معاينة Netlify (Draft Deploy)

الموقع العام منشور كمعاينة تجريبية (Draft Deploy) على Netlify، وليس نشرًا إنتاجيًا:

- الموقع: `c-cafe-preview` (`e5cdc6ec-a8af-4154-bba7-b97d4eea63f4`)، ولا يوجد نشر إنتاجي حاليًا؛ `https://c-cafe-preview.netlify.app/` يعيد 404.
- رابط المعاينة الحالي (Draft Deploy): `https://6af0598146d3333788ef1350--c-cafe-preview.netlify.app`.
- النشر من الملفات المحلية بلا GitHub وبلا commit أو push، وبلا دومين مخصص.
- رابط الـDraft Deploy ثابت لهذه الحزمة، وأي نشر جديد ينشئ رابطًا جديدًا؛ لا تُستخدم روابط قديمة للتحقق.

```bash
npm run build            # يبني dist/ من قائمة سماح صريحة (18 ملفًا)
npm run snapshot:content # يحدّث لقطة الاحتياط يدويًا (اختياري وليس جزءًا من البناء)
npm run preview:site     # يشغّل محاكي Netlify محليًا على المنفذ 8899
npm run check:preview    # يتحقق من الصفحة والأصول والروابط

# التحقق من رابط معاينة حقيقي
PREVIEW_URL=https://... EXPECT_PREVIEW=1 npm run check:preview
# التحقق من نسخة احتياطية متعمدة
PREVIEW_URL=https://... EXPECT_SOURCE=fallback EXPECT_PREVIEW=1 npm run check:preview
```

متغيرات المعاينة: `CCAFE_PREVIEW_ONLY=1` يضيف `X-Robots-Tag: noindex` ووسم `robots` إلى الاستجابات الحية، ويُضاف `noindex` دائمًا إلى الاستجابات الاحتياطية. **أزل `CCAFE_PREVIEW_ONLY` قبل أي نشر إنتاجي** حتى لا يُفرض `noindex` على الإنتاج. الاستجابات الاحتياطية تبقى `noindex` في كل الأحوال.

- `scripts/public-files.mjs` هي قائمة السماح الوحيدة؛ البناء يفشل إذا نقص أصل أو ظهر ملف ممنوع.
- `dist/` لا يحتوي `index.html` ولا `data/` أو `admin/` أو `supabase/` أو الاختبارات أو ملفات البيئة. `track.js` أصبح أصلًا عامًا، لكن الصفحة لا تحمّله إلا إذا فُعِّل التتبع صراحةً.
- الصفحة تُولَّد وقت الطلب من `netlify/functions/site.js`، لذلك لا يحجبها ملف ثابت. التوجيه في `netlify.toml` يرسل `/` و`/index.html` إلى الدالة بـ `force = true`.
- الدالة تقرأ `published_content` بالمفتاح العام فقط، ولا تستخدم `service_role` أو `SUPABASE_ACCESS_TOKEN`، ولا تعرض أي مسار كتابة أو إدارة.
- علامة النسخة: `<meta name="ccafe-content-version" content="...">`، وترويسات `X-CCafe-Source: live|fallback` و`X-CCafe-Version` و`X-CCafe-Reason`.
- عند فشل الاتصال أو انتهاء المهلة أو وصول بيانات غير صالحة تُستخدم لقطة ثابتة في `netlify/functions/content-fallback.json` مع `X-CCafe-Source: fallback` و`X-Robots-Tag: noindex`. اللقطة **ليست** بالضرورة آخر محتوى منشور، ولا يحدّثها البناء.
- لا كاش CDN للمحتوى الديناميكي في هذه المرحلة (`Cache-Control: no-store`).
- التتبع اختياري لكل نشر: لا يُضمَّن `track.js` ولا يُفعَّل `/api/track` إلا عند ضبط `CCAFE_ANALYTICS_ENV` صراحةً إلى `preview` أو `production`. في هذه المرحلة تُضبط على `preview` فقط. أي قيمة أخرى أو غيابها يعطّل الإدخال والإحصاءات معًا. فتح اللوحة أو معاينة المسودة لا يولّد زيارات، لأن معاينة المدير تُبنى بـ`analytics:false` وبلا سكربتات.
- زيارات المعاينة تُوسم `env='preview'` وتُعزل تمامًا عن `production` في التخزين والاستعلام والمسح؛ لا تُجمع أحداث من النشرات التجريبية القديمة لأن التتبع لم يكن مفعّلًا فيها. التشغيل المحلي عبر `server.js` يبقى كما هو ولا يرسل إلى Supabase.

متغيرات الدالة المطلوبة (أسماء فقط): `SUPABASE_URL` و`SUPABASE_ANON_KEY`. واختياريًا `CCAFE_SUPABASE_TIMEOUT_MS` (الافتراضي 5000 مللي ثانية) و`CCAFE_PREVIEW_ONLY` للمعاينة، وللتحقق من الظهور `CCAFE_VERIFY_ORIGIN` (أصل معاينة Netlify مسموح)، و`CCAFE_MEDIA_FINALIZE_TOKEN` لاعتماد الصور المرفوعة، وللتحليلات `CCAFE_ANALYTICS_ENV` (`preview` أو `production` فقط) و`CCAFE_ANALYTICS_INGEST_TOKEN` (64 hex). إن غاب `CCAFE_VERIFY_ORIGIN` يُستخدم `DEPLOY_PRIME_URL` ثم `Host` الذي يراه الخادم بعد قائمة سماح؛ لا يُقرأ أي URL من العميل. لا تُضاف `service_role` أو `SUPABASE_ACCESS_TOKEN` أو كلمة مرور قاعدة البيانات إلى Netlify.

`scripts/serve-site.mjs` محاكٍ محلي فقط، ولا يثبت سلوك Netlify الفعلي من حيث التوجيه أو الحزم أو الكاش. للتحقق الأقرب للحزمة استخدم `npx netlify-cli functions:serve --offline --functions netlify/functions`.

## لوحة إدارة المحتوى على معاينة Netlify

`/admin/` على رابط المعاينة يعرض المحتوى المنشور وسجل النسخ، ويسمح للمدير بتحرير **مسودة واحدة** وحفظها ومعاينتها ونشرها، واستعادة أي نسخة من السجل. مكتبة الوسائط تسمح للمدير برفع صورة خاصة واعتمادها بعد التحقق واختيارها في المسودة، وصفحة **نشاط الزوار** تعرض أحداث بيئة واحدة فقط للمدير:

- الدخول عبر Supabase Auth بالبريد وكلمة المرور. لا يوجد رابط سري ولا دخول تلقائي من localhost على Netlify، والتسجيل العام مغلق.
- بعد الدخول يتحقق الخادم من الـJWT عبر `/auth/v1/user`، ثم من العضوية في `public.admin_users` عبر `is_admin()` بمعرّف المستخدم نفسه. وجود جلسة وحدها لا يكفي، وإخفاء الواجهة ليس حماية.
- التحرير يشمل النصوص والروابط والإعدادات الموجودة وترتيب الأقسام وإظهارها/إخفاءها، ومراجع الصور عبر مكتبة الوسائط. لا حقول محتوى جديدة.
- قراءة المسودة للمدير عبر RLS، أو المحتوى المنشور عند غيابها. الحفظ عبر `admin_save_draft` والحذف عبر `admin_delete_draft`، والنشر عبر `admin_publish`، والاستعادة عبر `admin_restore`؛ وكلها `SECURITY DEFINER` تعيد التحقق من `admin_users` وتفرض `expected_version` و`expected_revision` داخل قاعدة البيانات. القراءة والسجل عبر JWT المستخدم نفسه، ولا يُستخدم `service_role` أو `SUPABASE_ACCESS_TOKEN` في Netlify.
- النشر يرسل **مراجعة المسودة المحفوظة** فقط (`expected_draft_revision` إلزامي، بلا محتوى من العميل) مع `expected_version` و`operation_id`. إعادة الطلب نفسه بعد انقطاع الرد تعيد نتيجة العملية نفسها ولا تنشئ إصدارًا إضافيًا، والنقر المتكرر محجوب أثناء العملية. النشر يحذف المراجعة التي طابقت فقط، فلا يحذف مسودة أحدث.
- الاستعادة تستخدم `content_history.id` الحقيقي مع `expected_version` و`operation_id`، وتنشئ إصدارًا جديدًا ولا تعيد ترقيم الإصدارات ولا تحذف أي نسخة. قبل التأكيد يوضّح الحوار أثر الاستعادة على المسودة الحالية، ويُحفظ آخر 50 إصدارًا.
- `/api/admin/bootstrap` و`/api/admin/history` و`/api/admin/preview` و`/api/admin/verify` و`/api/admin/analytics` تقبل `GET/HEAD`، و`/api/admin/draft` و`/api/admin/draft/delete` و`/api/admin/publish` و`/api/admin/restore` و`/api/admin/analytics/clear` تقبل `POST`. الجميع يعيد 401 بلا جلسة و403 لغير المدير و404 للمسارات الأخرى و405 للأساليب الأخرى.
- التحقق من الظهور منفصل عن نجاح الحفظ: يقرأ `/api/admin/verify` أصل المعاينة من إشارات الخادم فقط (`CCAFE_VERIFY_ORIGIN` ثم `DEPLOY_PRIME_URL` ثم `Host` بعد قائمة سماح)، ولا يقبل URL من العميل. يجب أن تكون الصفحة `X-CCafe-Source: live` وأن تطابق علامة النسخة؛ نسخة `fallback` أو نتيجة قديمة لا تُعد تأكيدًا. عند الفشل تظهر «تم الحفظ، تعذر تأكيد الظهور» مع زر «إعادة الفحص» فقط، دون إعادة نشر.
- الحفظ تلقائي بعد توقف قصير مع منع تداخل الطلبات (single-flight). الحالات: تغييرات غير محفوظة، جارٍ الحفظ، محفوظ، فشل الحفظ (مع إعادة المحاولة)، وتعارض.
- عند التعارض (HTTP 409) يبقى تعديل المستخدم في الواجهة دون استبدال صامت، وتعرض «مراجعة الفروق» الفرق بين نسختي والنسخة الأخرى قبل «إعادة تحميل النسخة الأحدث» أو «حفظ نسختي».
- تنبيه `beforeunload` عند مغادرة الصفحة بتعديل غير محفوظ، وحذف المسودة يتطلب تأكيدًا ويتحقق من revision.
- المعاينة للمدير فقط: تُجلب بالـJWT عبر ترويسة الطلب (الرمز لا يظهر في أي رابط)، ثم تُحقن في `iframe` بـ`sandbox=""` و`srcdoc`. تُزال السكربتات ويُضمَّن CSS الموقع، وتمنع CSP في مستند المعاينة السكربتات والإطارات والاتصالات، فلا تصل إلى جلسة اللوحة ولا تشغّل التتبع ولا تُكاش أو تُفهرس. خريطة Google المضمّنة تبقى محجوبة داخل المعاينة لهذا السبب، وتظهر داخل اللوحة ملاحظة بأن الخريطة والتفاعلات المحجوبة تُختبر على الموقع العام؛ عزل `sandbox` لم يُضعَّف.
- كل استجابات الواجهة والإدارة `no-store` و`noindex` مع CSP صارمة، والجلسة في الذاكرة فقط (`persistSession: false`) ولا تُحفظ في `localStorage` أو الكوكيز.
- تعارضات النسخ تُطلق SQLSTATE `PT409` (لا `40001`، لأن PostgREST يعيد المحاولة عليه حتى انتهاء المهلة) فتصل كـHTTP 409 فورًا. التفاصيل في `supabase/migrations/20261108020000_conflict_sqlstate.sql`.
- الواجهة تُقدَّم من `netlify/functions/admin-ui.js` لا كملفات ثابتة، و`netlify/admin/vendor/supabase.js` يُنسخ من حزمة `@supabase/supabase-js@2.119.0` المثبّتة عند `npm run build` (مستبعد من Git).
- لا يوجد حساب مدير نهائي في هذه المرحلة. في مرحلة النشر/الاستعادة أُنشئ حساب اختبار عبر **Auth Admin API**، ثم أُنهيت جلساته وحُذف عبر **Auth Admin API** أيضًا (لا حذف مباشر من جداول `auth`)، فبقي `auth.users=0` و`admin_users=0`. (في مرحلة سابقة حُذفت حسابات اختبار مباشرة بـSQL من جداول `auth`، وهو أسلوب غير معتمد ولا يُعاد استخدامه.)

## مكتبة الوسائط والرفع الخاص (2026-11-09)

الصور المرفوعة تُحفظ في bucket **خاص** اسمه `ccafe-media`، ولا تُخدم من أي رابط عام. تظهر قائمة بالأصول الأصلية الـ15 (للقراءة والاختيار فقط، دون نسخ أو تعديل) وبالصور الجديدة المعتمدة، بالعربية وRTL، للمدير فقط.

### المسار

1. `POST /api/admin/media` يتحقق من الاسم/النوع المعلن/الحجم، ثم يستدعي `admin_media_create` الذي يولّد مسارًا على الخادم بصيغة `media/<uuid>` ويعيد صفًا `pending`.
2. يرفع المتصفح الملف مباشرة إلى المسار نفسه في bucket الخاص بـJWT المدير. سياسة Storage تسمح فقط بإدخال المسار المطابق لصف `pending` أنشأه المدير نفسه، ولا تسمح بالاستبدال.
3. `POST /api/admin/media/finalize` يستحوذ على الصف أولًا عبر `admin_media_begin_finalize` (يمنع Storage أي حذف أو إعادة رفع للمسار طوال التحقق)، ثم ينزّل البايتات بـJWT المدير، يفكّها فعليًا بـ`sharp`، يشتق النوع والأبعاد والحجم وSHA-256 من المحتوى (لا من الامتداد أو MIME المعلن)، ويرفض SVG والملفات التالفة وما يتجاوز الحدود. عند النجاح فقط يستدعي `admin_media_finalize` بالبصمة الخادمية، فيصبح الصف `approved` وقابلًا للاختيار.
4. `POST /api/admin/media/abandon` يعلّم الصف `failed` ويحذف الكائن المؤقت. `admin_media_fail` idempotent ولا يمس صفًا معتمدًا.

### الأمان

- الرفع والاعتماد والقراءة تتطلب JWT مدير صالحًا؛ الزائر وغير المدير مرفوضان في الـAPI وRLS وStorage.
- لا يقبل الخادم رابط تنزيل أو مسارًا من العميل؛ المسار يأتي من صف أنشأه الخادم ويُعاد التحقق منه قبل أي طلب Storage.
- الملف يبقى خاصًا وغير قابل للاختيار حتى نجاح التحقق. إعادة `finalize` لملف معتمد تعيد النتيجة نفسها دون إعادة تحقق (idempotent)، وتعديل البايتات بعد الاعتماد يُرفض.
- إغلاق نافذة TOCTOU: `admin_media_begin_finalize` يسجل `verification_started_at` تحت قفل الصف، وتمنع سياسات Storage أي `INSERT`/`DELETE` للمسار أثناء وجود هذا الاستحواذ. `admin_media_finalize` يرفض صفًا غير مستحوذ عليه (`PT409`)، و`admin_media_fail` يمسح الاستحواذ ليبقى تنظيف الملفات المرفوضة ممكنًا. الاستحواذ idempotent، لذا إعادة المحاولة أو طلبان متزامنان لا يعيدان التحقق من بايتات مختلفة.
- `finalize` يحتاج سر الخادم `CCAFE_MEDIA_FINALIZE_TOKEN`؛ قاعدة البيانات تحفظ بصمة SHA-256 فقط في `public.media_secrets`. غياب السر يعيد `503 media_unavailable`. هذا بديل عن `service_role` (المرفوض في Netlify)، ونطاقه تحويل `pending` إلى `approved` بعد تحقق خادمي فقط. السر وحده لا يكفي: يلزم JWT مدير، وصف مستحوذ عليه.
- بيئة Netlify: خطة الحساب الحالية لا تسمح بتقييد `scopes` (يعيد API الرسالة `403 Upgrade your Netlify account to set specific scopes`)، كما أن تحويل المتغير إلى `is_secret` مرفوض لأن secret لا يعمل في `post_processing`. لذلك `CCAFE_MEDIA_FINALIZE_TOKEN` مقروء حاليًا لأعضاء الحساب وفي كل النطاقات. التوصية: تدويره عند أي شك (تحديث متغير Netlify + `media_secrets.value_sha256` + إعادة نشر)، وتقييده إلى `functions` وجعله secret إن رُقّيت الخطة.
- المعاينة للمدير فقط عبر روابط موقعة قصيرة العمر؛ تُخزَّن المراجع المنطقية `media/<uuid>` في المسودة، لا الروابط المؤقتة، فانتهاء الرابط لا يفسد المسودة.
- النشر يرفض أي مسودة تحتوي صورة خاصة جديدة برسالة واضحة `422 {error:'private_media'}`، على مستوى API (فحص مسبق) وRPC مباشرة (SQLSTATE `CC001`). نشر الأصول الأصلية `assets/` يبقى عاملًا.

### حزمة النشر و`sharp`

`admin-api` يحمّل `sharp` ديناميكيًا داخل `finalize`، فلا يستطيع مُجمِّع Netlify تتبعه. لذلك يضمّن `netlify.toml` (قسم `[functions.admin-api]`) الحزم `node_modules/sharp`, `detect-libc`, `semver`, `@img/colour`, وحزمتي Linux x64: `@img/sharp-linux-x64` و`@img/sharp-libvips-linux-x64`. على محطة Windows يجب جلب حزم Linux يدويًا (`npm pack @img/sharp-linux-x64@0.35.5 @img/sharp-libvips-linux-x64@1.3.4` ثم فكّها داخل `node_modules/@img/`) قبل `netlify build`، وإلا يفشل `finalize` بـ`422 invalid_image` مع `reason=verifier_unavailable`. النشر يُبنى بـ`netlify build` ثم `netlify deploy --no-build --dir dist --functions .netlify/functions`؛ لا يُستخدم `--remote` لأن المشروع غير مربوط بمستودع Git.

## تحليلات نشاط الزوار (المعاينة)

الأحداث التي يجمعها `track.js` هي نفسها بلا إضافة: `pageview` و`section` و`mood` و`click` و`leave`، والمؤشرات والفترات (`today` و`7d` و`30d` و`90d`) بقيت كما هي. لا تتبع جديد ولا مؤشرات جديدة.

### المسار والصلاحيات

1. الصفحة العامة تحمّل `track.js` فقط عندما تكون `CCAFE_ANALYTICS_ENV` صريحة. يرسل السكربت حدثًا صغيرًا إلى `POST /api/track`، وهو المسار الوحيد للكتابة.
2. `netlify/functions/track.js` يتحقق من الطريقة والحد الأقصى للجسم (4096 بايت) ويستبعد الروبوتات، ثم يعيد التحقق من كل حقل عبر `sanitizeEvent` المشتركة. لا يثق بأي قيمة زمنية أو هوية من العميل: الوقت وبصمة الزائر اليومية يُحسبان على الخادم.
3. البصمة اليومية = `HMAC-SHA256(CCAFE_ANALYTICS_INGEST_TOKEN, "visitor|env|day|ip|ua")` مقتطعة إلى 16 hex. لا IP خام ولا User-Agent ولا كوكيز ولا بصمة دائمة، ولا يمكن ربط الزائر بين يومين أو بين بيئتين. تصنيف الجهاز/المتصفح/النظام يتم من User-Agent على الخادم.
4. يرسل الخادم إلى `analytics_ingest` بصمة الطبقة الأولى فقط `D1 = SHA-256("ingest|" + token)`، وليس السر نفسه. القاعدة تخزّن `D2 = SHA-256("ingest|" + D1)` وتعيد تجزئة القيمة الواردة قبل المقارنة؛ لذلك لا تُخزَّن القيمة التي ترسلها الدالة، ولا تُقبل البصمة المخزنة نفسها كاعتماد. الدالة تكرر كل قيود الحقول والأنواع والأطوال قبل أي كتابة.
5. `analytics_ingest` ممنوحة لـ`anon` عمدًا لأن دالة Netlify تستخدم المفتاح العام، لكنها ترفض أي استدعاء مباشر لا يحمل `D1` الصحيحة. إرسال `D2` المخزنة أو السر الخام أو أي قيمة أخرى يُرفض بـ`42501` قبل أي كتابة أو استهلاك للعدّاد. الجداول الثلاثة مغلقة تمامًا أمام `anon` و`authenticated`، وليس فيها سياسات RLS. `admin_analytics_snapshot` و`admin_analytics_clear` تتطلبان `assert_admin()`؛ لا يستطيع الزائر أو المستخدم غير المدير قراءتها أو مسحها حتى عبر PostgREST مباشرة.
6. صفحة `#stats` في اللوحة تُقدَّم كملف مستقل `netlify/admin/stats.js` عبر `window.CcafeStats.mount(...)`. لا تحمل أي اعتماد بنفسها: تستخدم دوال `app.js` الممرَّرة، فيبقى JWT في الذاكرة فقط. تعرض loading/empty/error بوضوح، والمسح يتطلب تأكيدًا يشرح أن المسح مقصور على بيئة واحدة وأنه غير قابل للاستعادة.

### الإعداد والتعطيل

- إعداد المعاينة في Netlify (Functions scope، موقع `c-cafe-preview` فقط): `CCAFE_ANALYTICS_ENV=preview` و`CCAFE_ANALYTICS_INGEST_TOKEN=<64 hex>`. السر الجديد لا يُعاد استخدامه مع `CCAFE_MEDIA_FINALIZE_TOKEN`، ولا يُضاف إلى المتصفح أو إلى Git. تُخزَّن بصمته من الطبقة الثانية `D2` فقط في `public.analytics_secrets`، فلا تصلح حتى لو تسربت كاعتماد مباشر. ملفات الترحيل تحتوي بصمات وهمية خاملة؛ بعد تثبيت جديد أو استعادة، حدّث `public.analytics_secrets` و`public.media_secrets` من السرين المولّدين أو من صفوف النسخة الاحتياطية، ولا تعتمد على قيم الترحيل.

- التعطيل الكامل: أزل `CCAFE_ANALYTICS_ENV` (أو اتركه فارغًا) وأعد النشر. تتوقف الدالة عن الإدخال، وتختفي الصفحة، ولا تُحمَّل `track.js`؛ تبقى الأحداث المخزنة كما هي حتى تنظيفها أو مسحها.
- تعطيل التنظيف وحده: `select cron.unschedule('ccafe_analytics_purge');` على المشروع، أو استدعاء الدالة يدويًا عند الحاجة. لا تُمنح الدالة لأي دور API.
